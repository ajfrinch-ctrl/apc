# Teacher panel full-system audit and redesign specification (draft)

**Started:** 2026-11-10 · **Scope confirmed:** 2026-11-11
**Status:** Preliminary and incomplete. This document is not approved; no further Teacher implementation is authorized until the user reviews and approves the completed inventory and specification.

## Confirmed full-system scope

The user wants the whole Teacher panel's internal system changed everywhere, including all screens, navigation, layouts, forms, workflows, data loading/saving, role and permission gates, notifications, and integrations. This includes a complete visual redesign, while preserving every existing feature and all stored records. The audit must therefore cover static markup plus dynamically mounted modules and route/deep-link paths—not just the visible shell or navigation cards.

The prior 20 navigation answers remain binding: distinct full-screen in-shell pages with URL/hash changes; browser Back/Forward; persistent five-seat bottom navigation; a fixed thumb-reachable Back control; list then separate detail pages; no full detail inline; same route model on mobile/desktop; preserve list/filter/scroll/form state; hide unauthorized features; filters/tabs/form controls remain local; record actions remain on that record's detail page. The user has now also confirmed that the redesign scope includes data/permissions/integrations and that all features and records must be retained.

**Required next deliverable before code:** a complete control-by-control inventory that maps every static and dynamic clickable control, field, route, data source/write path, permission, side effect and current defect, followed by the end-to-end information architecture, screen/component design, data/permission/integration migration plan, state/history rules, preservation safeguards, and acceptance tests. Present the completed document for review and wait for explicit approval before implementation.

## Work sequence (step by step)

1. **Scope and shell** — confirmed; inventory global controls, all route/view names, the bottom navigation, Home and empty/error/loading states.
2. **Feature surfaces** — inventory every static and dynamically mounted feature, its buttons, tabs, filters, forms, modal/detail flows and current behavior.
3. **Data, permissions and integrations** — trace reads/writes, ownership/scope rules, role gates, sync/storage sources, notifications, external modules and failure recovery.
4. **Complete redesign specification** — propose the page hierarchy, visual system, component/workflow changes, route/history/state rules, migration/preservation safeguards and measurable acceptance tests.
5. **User review gate** — present inventory and specification together; make no Teacher implementation changes until explicit approval.
6. **Implementation after approval** — work in small feature batches, testing each batch and retaining all existing data/features.

## Agreed navigation contract

- A destination opens a full Teacher-shell screen, updates the hash, survives refresh/deep link, and participates in browser Back/Forward.
- The shared five-seat bottom bar remains visible. A fixed bottom Back control is available on non-Home screens.
- List/detail flows are separate screens. Full descriptions and record actions do not expand in the list row.
- Clicking a feature card/row opens its destination; internal filters, search, tabs, and simple status controls remain controls on the current screen.
- Home shortcuts open their feature directly. The Exams feature remains a single hub. Academic tools, class/routine/attendance/student work, Profile, Settings, and notifications have distinct destinations.
- Returning preserves the prior filter, scroll, and unsaved draft state where applicable. Unauthorized feature entry points are not exposed.
- Desktop and mobile share the same route model.

## Acceptance checks

1. Every visible Teacher feature card, header icon, class/record row, and enabled bottom seat has an explicit destination or is documented as a same-screen control/action.
2. Feature entry changes the Teacher screen and hash; refresh opens the same destination.
3. Browser Back/Forward returns to the exact prior screen; Back control uses the same route stack and falls back to the proper parent when a page was opened directly.
4. No full activity, notice, class, student, course, or attendance-session details are expanded in a list/dashboard row.
5. Search, filter, routine tabs, exam-hub mode tabs, theme switches, and chapter status controls do not create unnecessary route entries.
6. Home shortcuts deep-link directly; all list/detail pages preserve the parent list's filter/scroll on return.
7. Direct routes remain role-gated, and unavailable features do not reveal protected data.
8. The same behavior passes at mobile and desktop viewports, and the persistent bottom navigation remains available.

### Step 2 findings and limitations

- The Teacher shell has several independently mounted modules; a markup-only scan cannot see all optional controls, permissions, or state-dependent actions.

- The exam hub, lecture studio, reports, chat, notifications/settings and account modules each own their own controls and persistence behavior; they cannot safely be redesigned from `teacher.html` alone.
- Step 2 is a discovery draft, not the requested final “nothing omitted” inventory. Step 3 is now underway below; it is not complete.

### Teacher runtime lifecycle and event wiring (source trace)

1. `hasStaffSession('teacher')` and the admin registration/entry switch gate determine whether the Teacher shell opens. A valid session gets the current hash parsed; unknown route names fall back to Home. The session watcher can lock the panel after entry; the panel guard prevents cross-panel links.
2. `reload()` resolves the active Teacher profile, sets username + staffId scope, best-effort projects directory assignment rows, then concurrently loads teaching records, approved assigned students, courses and teacher-filtered exams; it then resolves effective assignments and re-renders. Course/exam errors are caught to empty/unavailable snapshots, while a teaching/roster failure sets the global data error/retry state.
3. Settings account group, Settings hub, course editor, Reports and profile self-edit are mounted at panel startup. Chat, notification history and lecture-sheet studio are lazy-mounted on first entry. These modules have their own internal state and error handling.
4. Teacher activity/course/assignment watchers, storage events and `apc-sync-updated` trigger debounced reloads. Exam updates refresh exams/home separately. The refresh is suppressed while a save is busy or the shell is hidden; it is also suppressed while the shared Teacher modal is open. Keep a user’s in-progress form from being silently replaced by a live update.
5. Notification bell/history clicks are captured before the shared notice-center listener and route to Teacher notification history. Record, class, student, course and notice card clicks are delegated at document level. In a detail route, old modal-style form actions render inline inside the detail page; other forms use the shared modal. Escape, backdrop, close button and cancel share `closeModal()`; modal keyboard focus is trapped and restored.
6. Detail hash uses `kind/<encoded-id>` and includes activity create, class, student, course, notice, attendance and password kinds. `history.state` tracks Teacher depth for safe Back fallback. Routine category tabs intentionally collapse to `#routine-view`; the exam hub mode and report/course mode are local state and not separate hash routes. Switching activity type clears that type’s search and resets paging; `setView()` scrolls Teacher main to top. These are current state semantics, and filter/scroll restoration remains an explicit design decision rather than a guaranteed existing behavior.

This lifecycle map is source-derived; confirm with refresh/back/live-update E2E assertions before finalizing detailed interaction specs.

### Stored-record invariants surfaced so far

- **Teaching activity**: stable id; type (`exam` is fenced off to exam manager), title, subject, class/group and normalized class/section keys, details, room/resource URL, date/time/duration/marks, draft/published status, owner ID/name, timestamps, optional routine-slot ID, and a per-student progress object. Progress may carry status/value, teacher comment, student answer or attachment URL, update time and related attendance grade-audit rows. Validation caps text/URLs and enforces status/date/time/range rules; changing class/group is refused after progress exists; overlapping published exam/routine times are refused.
- **Course**: stable id, class/section and subject, owner, publish/draft state, create/update timestamps, and ordered chapters with stable IDs, title, status and completion date. Teacher sees owned courses in the assigned scope. Existing course/chapter delete operations are real hard deletes and the current detail controls do not show an explicit confirmation. Retain the user-requested delete feature, but use an explicit record-specific confirmation and never delete records merely during migration/layout changes.
- **Course-content / lecture sheet**: stable content ID, class/subject/chapter IDs, type, title/description/content/attachment, author and timestamps, published/active state. Lecture sheets additionally carry sanitized structured document JSON, page settings, status/published timestamp, document version and bounded history; optimistic version mismatch and crash-recovery drafts are supported. Archive is soft (`active:false`), whereas an explicit delete is permanent. Keep the original source PDF / exact generated PDF artifact behavior already validated for student reading/download.
- **Exam**: stable exam/question/attempt IDs and codes; title, class/group/subject, type, schedule/duration, instructions, marks/pass/negative configuration, chapter/topic metadata, question/option ordering, review status/note and timestamps; participant roster, absent IDs, answers/order, attempt status/number/timing and results. Paper edits are locked after state/attempt constraints; preserve audit/review history and private answer-key handling.
- **Notice**: stable id, title/body, category, class/group audience, status, creator role/identity, created/updated timestamps and class key. Teacher list is creator-scoped. Toggle publication and delete are separate destructive/status actions; current notice delete is immediate rather than confirmation-gated. Add confirmation without losing the feature; local “written here” notification bookkeeping is not part of the shared notice record.

This is a schema summary, not a migration schema. Preserve unknown/legacy optional fields when editing records, keep stable identifiers, and do not normalize by rewriting the entire store unless the migration is separately tested and non-destructive.

### Backend authorization caveat and existing V2 work — explicit specification item

The client repositories enforce Teacher session, own-record and assignment scope, but the checked-in shared cloud path is broader. `README.md` and `docs/INTERIM-ANONYMOUS-SYNC.md` explicitly document that default local mode still starts the legacy anonymous `activePlusSync/v1` bridge; current `database.rules.json` permits collection reads/writes with `auth != null`, and the README warns that anonymous callers may access sensitive roster, ledger and password-hash data. The Supabase RLS migration also allows `anon, authenticated` to paths under `activePlusSync/v1`. `?backend=firebase` disables the legacy bridge but is a separate staged auth/backend mode, not a casual fix or drop-in toggle. Do not deploy or alter this path as part of visual changes.

There is already a substantial **staged V2** security design: `database.rules.v2.draft.json` + its generator/simulator, `sync/notices-v2-policy.js`, `sync/notices-v2-sync.js`, and non-destructive cutover/rehearsal tests. The V2 model uses real Auth claims, per-teacher drafts, assignment-checked publish, student-scoped projections and server-side authorization. But `firebase.json` still deploys `database.rules.json`, and `rtdb-v2-draft-rules.test.mjs` explicitly asserts that the draft is not deployed. The staged V2 notice sync is wired but claims-gated/no-op without eligible non-anonymous claims; it runs alongside the v1 bridge rather than replacing it. The V2 rules are simulator-tested and must still pass the documented Firebase Emulator suite before deployment. Separately, `docs/FIREBASE-SYNC-AUDIT.md` says the secure general-purpose sync foundation is partial/not deployed.

**Redesign consequence:** preserve existing UI checks, but do not represent them as server authorization or promise the current sync is secure. The final proposal must treat “Teacher panel redesign” and “secure backend cutover” as linked but distinct workstreams, describe current risk plainly, assess reuse of the existing V2 plan, and provide a staged non-destructive rollout/rollback plan. Because enabling/disabling the legacy bridge or deploying V2 changes app-wide sync and access (not just Teacher UI), make the boundary explicit for user review. No rule, provider, sync-mode or data migration was made in this audit.
